# Day 25：Resume、拒绝审批与安全恢复

日期：2026-11-06。状态：**COMPLETED（单进程命令行练习）**。前置：Day 23 checkpoint、Day 24 interrupt。本课不接页面、不调用模型、不接真实订单系统。

## 1. 真实场景与目标

订单 124 的退款状态变更已经停在审批节点。主管可以拒绝或批准；普通员工、过期申请、参数被改、重复点击和订单版本变化都必须被拦下。用一个独立命令观察“中断 → 校验 → `Command` 恢复 → 条件路由 → 结果”。

## 2. 重点代码与执行

[源码](../../../apps/api/src/day25-resume.ts)中，`approval` 节点在首次运行时暂停，恢复时 `interrupt` 返回审批决定；条件边把两种决定送往不同节点：

```ts
.addNode("approval", (state) => {
  const decision = interrupt<Preview, Decision>(state.preview);
  return { decision };
})
.addConditionalEdges("approval", (state) => state.decision, {
  approve: "apply", reject: "reject",
})
```

恢复入口先查待审批记录、审批人、申请人与审批人分离、有效期、图是否停在审批节点、参数哈希，再调用：

```ts
const result = await graph.invoke(
  new Command({ resume: decision }),
  { configurable: { thread_id: threadId } },
);
```

`apply` 节点再检查订单当前状态和版本，之后才改变演示内存订单。`reject` 节点只返回结果，不触碰订单。`thread_id` 用来找 checkpoint；演示中的 `approvals` Map 是审批记录，二者不是一回事。执行 `pnpm --filter @ai-native-console/api day25:resume`。

## 4. 本课专项五大深水坑

| 风险 | 本课做法 | 仍需补足 |
| --- | --- | --- |
| 非审批人伪造决定 | `actor` 与 `approver` 比对，申请人不可自批 | 真实认证和租户权限尚无 |
| 旧申请过期 | 恢复前检查 `expiresAt` | 生产时用数据库时间及持久记录 |
| 改卡片参数后批准 | 比较提交的哈希、记录的哈希和 checkpoint 预览 | 哈希不是授权凭证 |
| 重复批准或并发批准 | 已处理状态拒绝顺序重复点击 | Map 无原子事务，并发/多实例仍不安全 |
| 审批后订单已变化 | `apply` 比较版本和旧状态 | 真实写入需数据库条件更新及幂等键 |

## 6. 模拟面试

**Q1：`Command({ resume })` 如何接上 `interrupt()`？** 推荐回答：用同一 `thread_id` 找到 checkpoint，图重新进入暂停节点，`interrupt` 返回 resume 值，然后条件边决定批准或拒绝路径。追问：是原 HTTP 请求一直挂着吗？不是，恢复是新的调用。错误答案：“把 `approved=true` 写到前端状态即可”。

**Q2：为什么恢复前后都要校验？** 推荐回答：恢复前核对审批人、过期、参数和图状态；执行前重新查订单状态与版本，防止审批期间订单被其他流程改变。追问：哈希能证明谁点了批准吗？不能，身份靠服务端认证。错误答案：“模型给出正确订单号就可以执行”。

**Q3：本课的重复批准拒绝能保证生产幂等吗？** 推荐回答：只能说明这个单进程顺序练习拒绝了第二次调用；Map 和普通状态赋值没有跨进程原子性。生产需持久审批记录的条件更新、业务幂等键和数据库事务。追问：进程重启后呢？MemorySaver 与 Map 都会丢，必须换持久存储。错误答案：“有 `thread_id` 就不会重复执行”。
