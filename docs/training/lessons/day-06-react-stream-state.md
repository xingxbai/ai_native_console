# Day 06：React 流式消费与消息状态管理

日期：2026-10-28。状态：COMPLETED。本课只改变前端展示状态，不接多轮记忆、取消传播或 Partial JSON；没有新增或修改 `.test.ts`。

## 1. 目标、前置与完成定义

前置是 Day 05 的 `start/delta/done/error` 协议和真实 DeepSeek 流。目标是让用户连续提问时看到各次问题、增量正文、完成或失败状态，并在阅读旧记录时不被强制滚动。完成定义：流式 `done` 才进入完成态；失败保留已收到正文并显示错误；单次请求期间禁止再次提交。

## 2. 概念与数据流

页面使用 `Exchange[]`：每项有问题、`loading/streaming/complete/error`、正文、错误与请求 ID。提交时追加 `loading`；`delta` 更新当前项；`readStreamReply` 只有读到合法 `done` 才 resolve，因此随后标记 `complete`。此记录仅在当前页面内存中；请求体仍只有本次 `message`，不是会话记忆。当前只有一个 Client Component 持有这些状态，暂不需要 Zustand；跨组件 run/审批状态到后续课程再评估。后续按用户要求删除了当时用于对照的完整回复路径，当前只保留流式路径。

滚动容器距底部不足 80px 时自动跟随更新；用户上滚后停止跟随。提交新问题时重新跟随。这样长回答可实时阅读，旧记录不会被新 token 抢走视线。

## 3. 实施与真实操作

改动 `apps/web/app/ask-panel.tsx`。在已有运行环境打开 <http://127.0.0.1:3100>，提交一个面试题；观察“等待回复 → 正在回复 → 已完成”、正文增量和请求 ID。再问第二题，确认第一题保留。长回复时向上滚动，确认视图停留；滚回底部后确认继续跟随。每次请求都调用真实 DeepSeek 并计费。

## 5. 本课专项五大深水坑

| 场景 | 后果与处理 | 验收 |
| --- | --- | --- |
| 用单个 result 覆盖上一题 | 用户失去上下文；改为按 id 更新 `Exchange[]` | 连问两题，第一题仍可见 |
| 有 delta 就当成功 | 半截答案被误用；只在 `done` 后标完成 | 断流显示失败而非完成 |
| 失败时清空片段 | 无法判断中断位置；保留正文并显示错误 | 中途失败可见片段与错误 |
| 每次更新强制滚底 | 阅读旧内容被打断；只在接近底部时跟随 | 上滚后视图不跳动 |
| 把页面记录当模型记忆 | 误称多轮对话；API 只发当前问题 | Network 请求体只有 `message` |

## 7. 常见问题排查

流式一直“等待回复”：检查 Network 的状态和 SSE 事件。出现片段后显示失败：确认有无 `done`，不要把片段当最终结果。旧记录消失：检查是否刷新页面；当前记录只存在内存。滚动不跟随：先滚回容器底部附近。

## 三、模拟面试真实考场

### Q1：流式 UI 如何设计状态？

**回答：** 我用每次请求一条记录，状态从 loading 到 streaming，再由 `done` 进入 complete；错误可从中间状态进入 error。正文和状态分开保存，所以失败时仍能展示片段。**追问：HTTP 200 就完成吗？** 不是，流中途可能失败，必须等协议终态。**错误答案：**“收到第一个 delta 就成功”。

### Q2：如何避免自动滚动干扰阅读？

**回答：** 读取滚动容器当前位置，只在距底部较近时跟随新增内容；用户上滚后暂停，下一次主动提交再跟随。**追问：为什么不每个 token 都 `scrollIntoView`？** 它会夺走正在阅读旧记录的用户视线，也可能造成额外布局开销。**错误答案：**“每次 render 都滚到底”。

### Q3：多条页面记录算多轮 Agent 记忆吗？

**回答：** 不算。记录只是 React 本地展示状态，当前 API 每次只发送一个 `message`，模型看不到之前的问题。真正的记忆还需要服务端会话隔离、历史选择和 token 预算。**追问：什么时候用 Zustand？** 多组件共享会话、run 或审批状态且局部 state 传递复杂时再引入；单组件无需全局 store。**错误答案：**“页面能显示历史，模型就能记住历史”。
