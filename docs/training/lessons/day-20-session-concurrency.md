# Day 20：会话隔离、并发与重复请求

日期：2026-11-05。状态：**IN_PROGRESS**。前置：Day 07 取消、Day 13 工具权限、Day 18 浏览器历史。本课只做当前页面的会话提交策略；系统尚无登录、租户、持久会话或多进程共享状态。

## 1. 真实场景与核心概念

用户连续点两次“提问”，可能发出两次模型调用，产生两份费用；第一条流还没结束又发第二条，迟到的回复可能覆盖界面。另一个浏览器标签页却应能独立提问。本课让每个页面实例持有随机 `sessionId`，每次提交有独立 `requestKey`。服务端按会话只允许一个进行中的请求，并在十分钟内拒绝同键重放。

流程：`页面生成 ID/key → Next/Fastify 校验 → 同步占位 → 模型或工具流 → 终态/断连释放占位`。`requestKey` 是请求去重键，不是 Fastify 的 `requestId`：前者由调用方保持，用于判断是否重复；后者由服务端生成，用于日志追踪。当前没有写操作，所以只演示“避免重复模型调用”，不宣称订单修改已实现幂等。

## 2. 重点代码

`apps/web/app/ask-panel.tsx` 在提交时先检查 `activeRequest.current`，再生成会话 ID 和请求键；`packages/contracts/src/index.ts` 对两个值做 UUID 校验。Next 代理透传，Fastify 在发流前调用 `reserve`：

```ts
const key = `${sessionId}:${requestKey}`;
if (active.has(sessionId) || seen.has(key)) return false;
active.set(sessionId, requestKey);
seen.set(key, now + RETAIN_MS);
return true;
```

`apps/api/src/session-requests.ts` 用内存 Map 记录活动会话与十分钟内的键；`release` 只在当前键仍匹配时释放，避免旧请求的迟到清理误删新请求。冲突返回 HTTP 409 / `REQUEST_CONFLICT`，页面显示中文提示。请求正常结束或断连都清理活动占位，但已见过的键在期限内仍不能再次执行。

这不是鉴权：请求中的会话 ID 可伪造，且为了兼容旧调用方两个字段暂为可选。真实 owner/tenant 归属、跨实例共享存储和带结果的幂等重放需要登录及持久状态，后续安全与工作流课程再做。

## 3. 通用五大深水坑

| 深水坑 | 本课关系 |
| --- | --- |
| 流式 / Partial JSON / Generative UI | 相关：只在当前流终态更新对应记录；不同模式不共享内容缓冲。 |
| 工具参数与自我纠错 | 相关：请求键不能替代工具参数和权限校验。 |
| 上下文与 Token | 相关：并发重复调用会重复消耗模型 Token；历史仍由当前页面提交。 |
| HITL 与副作用安全 | 暂不展开：写操作需要持久幂等记录与审批，内存键不足以保护。 |
| 取消、断流与恢复 | 本课重点：断连释放活动占位，同键仍不重新执行；没有 SSE 重放。 |

## 4. 本课专项五大深水坑

| 风险 | 触发、表现、原因 | 处理与验收 |
| --- | --- | --- |
| 双击提交 | React 状态尚未刷新时两次 handler 同时进入 | 同步检查 `activeRequest.current`；浏览器双击待手动验。 |
| 同会话并发 | 同一会话有两个不同键，回复交错 | 服务端第二个返回 409；无服务操作已验。 |
| 不同会话串扰 | 另一标签页也被误拒绝 | 按会话 ID 分开占位；无服务操作已验。 |
| 旧请求迟到清理 | 旧请求结束后删除新请求的活动状态 | `release` 比对请求键再删；无服务操作已验。 |
| 把去重键当身份或持久幂等 | 伪造会话 ID、服务重启或多实例导致保护失效 | 明示演示边界；真实项目需登录身份、共享存储和持久执行记录。 |

手动验收：浏览器 Network 勾选 Preserve log，同一页快速双击“提问”，应只有一个请求；复制相同 `sessionId/requestKey` 再提交，API 应回 409；不同标签页应有不同会话 ID 并可分别提问。停止生成后新请求使用新键应可继续。不要把页面生成的 ID 当作用户身份。

## 6. 模拟面试

**Q1：`requestId` 和 `requestKey` 有何区别？** 推荐回答：`requestId` 由服务端生成，用于关联日志；`requestKey` 由提交方生成并在重试时保持，用于识别同一次意图。本课只在单进程十分钟内拒绝重放。追问：同键重放会拿到原回答吗？答：不会，返回 409，没有结果缓存。错误答案：“两个都是 UUID，作用一样”，忽略生命周期与语义。

**Q2：如何处理同一会话两条并发问题？** 推荐回答：当前策略是串行，前端 ref 同步阻止第二次提交，服务端按 `sessionId` 再拦一次；不同会话互不阻塞。追问：另一进程能看到这张 Map 吗？答：不能，生产要共享状态。错误答案：“按钮 disabled 就够了”，绕过前端或 React 渲染前仍可提交。

**Q3：现在能说实现了租户隔离和写操作幂等吗？** 推荐回答：不能。会话 ID 来自客户端，没有登录 owner/tenant 绑定；键只在内存保留十分钟，重启会丢，且没有写操作执行记录。追问：真实改订单至少还要什么？答：服务端身份/归属校验、持久幂等键和结果、审批与审计。错误答案：“有 UUID 和 Map 就安全”，无法解决伪造、重启和多实例。
