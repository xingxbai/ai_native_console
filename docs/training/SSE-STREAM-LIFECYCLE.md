# SSE 流式请求生命周期与取消速查

适用范围：当前项目的 `POST fetch + SSE` 文本问答。浏览器向 Next.js 发请求，Next.js 代理到 Fastify，Fastify 调用 DeepSeek。本文关注传统一次性 HTTP 请求中不太显眼的事：响应已开始后如何判断完成、用户停止或离开页面后谁负责取消、弱网和断网有什么区别。

## 先记住四个不同的“结束”

| 现象 | 含义 | 页面应怎样处理 |
| --- | --- | --- |
| 收到 HTTP 200 | 响应头成功发送；模型仍可能继续生成或中途失败 | 继续读流，不能标成功 |
| 收到 `delta` | 一段文本到达；可能只有半个答案 | 展示片段，保持“正在回复” |
| 收到合法 `done` | 本项目协议确认这次回复完整 | 标“已完成” |
| 连接 EOF，但没有 `done` | 流提前结束、网络中断或上游故障 | 标失败，保留片段；不能当完整答案 |

`reader.read()` 给的是任意大小的网络字节块，和模型 token、SSE 事件都没有一一对应关系。SSE 的 `error` 事件是**响应头已发出后**传递模型错误的方式；此时不能再把 HTTP 200 改成 500。

## 当前链路中谁感知取消

```text
浏览器 fetch + AbortController
  -> Next Route Handler 的 request.signal / 返回流的 cancel()
  -> Next 到 Fastify 的 fetch signal
  -> Fastify 响应提前 close
  -> ModelProvider 的 AbortSignal
  -> AI SDK / DeepSeek 网络请求
```

点击“停止”时，[页面](../../apps/web/app/ask-panel.tsx)立即把当前记录标为“已停止”并调用 `abort()`，已显示的文本仍保留。Next [流式代理](../../apps/web/app/api/chat/stream/route.ts)监听 `request.signal`，也在下游响应流的 `cancel()` 中中断到 Fastify 的 fetch。[Fastify](../../apps/api/src/app.ts)只在响应**提前**关闭时调用模型取消信号；[模型适配层](../../apps/api/src/model-provider.ts)把该信号与 20 秒超时信号一起交给 AI SDK。

这是代码上的取消路径。浏览器关闭、断网时 Next 是否触发 `request.signal` 或流 `cancel()`、多久触发，以及 DeepSeek 是否及时停止，当前尚未做运行时断连验收。**前端 `abort()` 不能单独证明模型已停止，也不能撤销已产生的 token 费用。**

## 常见场景对照

| 场景 | 浏览器和页面 | Next / Fastify / 模型 | 当前可确认的边界 |
| --- | --- | --- | --- |
| 正常生成完成 | 连续显示 `delta`，收到 `done` 后标完成 | 模型流自然结束，Fastify 写完响应；正常 `close` 不再取消模型 | `reply.raw.writableFinished` 用于区分正常写完和提前断开 |
| 用户点“停止” | 页面主动 `abort()`，显示“已停止”并保留片段 | 代理应取消上游；Fastify 提前 `close` 后把信号传给模型 | UI 和信号传递已实现；各层实际停止时间未测 |
| 关闭标签页或浏览器 | 页面消失，不能依赖 React 卸载回调一定执行 | 底层连接通常断开；Next 可能通过 `request.signal` 或返回流的 `cancel()` 感知 | 哪个回调触发及触发速度须在目标环境实测 |
| 正常路由跳转或组件卸载 | 当前组件清理时调用 `abort()` | 后续路径同主动停止 | 只适用于组件清理确实执行的导航；关闭浏览器不能仅靠它 |
| 弱网、传输很慢 | 可能长时间停在“正在回复”，也可能一批文字同时到达 | 连接未断时不会因为“慢”自动触发取消；代理或平台可能缓冲 | 当前没有独立的无数据心跳或慢连接监控；不能仅凭 UI 停顿判定模型停止 |
| 完全断网 | 浏览器最终可能得到读流错误或 EOF | 连接断开被各层发现可能有延迟；模型在此期间可能继续生成 | 不能保证即时发现或零费用；没有断线重连 |
| DeepSeek 20 秒超时 | 若流仍在，可能收到终止 `error` 事件 | 模型适配层的 deadline 中止请求并归类为超时 | HTTP 200 后发生超时仍由 SSE 事件表达 |
| Next 到 Fastify 25 秒超时 | 页面可能读流失败或在建流前收到 504 | 代理取消上游 fetch | 建流前和建流后表现不同；当前未做故障注入 |

## 为什么正常 `close` 不等于“用户取消”

Node 的响应正常写完也会触发 `close`。当前 Fastify 只在 `!reply.raw.writableFinished` 时 `abort()` 模型；正常完成时模型流已自然结束，不需要再发送取消。这个判断避免把正常完成误记为断连。它不能单独证明供应商侧的实际终止时间。

## 弱网时最容易误判的三件事

1. **“文字没动”不等于模型停止。** 模型可能还在生成，也可能是网络、Next 或中间代理在缓冲；要看 Network 中是否持续到达 SSE 事件。
2. **“浏览器请求取消”不等于费用为零。** 已生成的内容和计费不能回滚，供应商收到中止信号也可能存在传播延迟。
3. **“SSE 有 `id`”不等于能续传。** 当前事件 ID 只用于本次流的顺序校验；没有保存事件、`Last-Event-ID` 处理或模型任务恢复。断线后重新提交会产生一个新请求。

## 排查顺序

1. **看页面状态：** 是“正在回复”“已停止”“回复失败”还是“已完成”？只有 `done` 允许完成。
2. **看浏览器 Network：** 请求是否取消、响应是否为 `text/event-stream`、最后一个事件是否为 `done` 或 `error`。关闭浏览器时可先在独立窗口或服务端侧观察，不能依赖已关闭页面的 DevTools。
3. **看 Next 代理：** `request.signal`、下游流 `cancel()`、上游 fetch 是否实际中断。不同部署环境可能行为不同。
4. **看 Fastify：** 响应是否提前 `close`，当时 `writableFinished` 是什么；正常完成不应误判。
5. **看模型侧：** SDK 是否收到 abort、DeepSeek 请求何时停止。只看到前端取消不足以得出这一结论。
